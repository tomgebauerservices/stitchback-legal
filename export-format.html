Stitchback – Merge & Undo for Jira: Export Format

Online register of data structures and formats (Article 26(b) of Regulation (EU) 2023/2854)

Version 1.0 · 31 October 2026 · format stitchback-export/1, merge record version 3

1. How to get the export

A Jira administrator opens the Product's administration page (Jira settings → Apps) and selects "Export all merge records". The page shows the export as JSON text; copy it and save it as a .json file. The Product checks on every request that the user is a Jira administrator. The export contains every key that the Product stores for the installation. Nothing stored is left out.

Every merge record is deleted automatically 90 days after its last activity, including a merge that stopped part-way (End User Terms, Section 10.4). An export contains the records stored at the time of the export.

2. Standards

  • JSON as defined in RFC 8259, encoded in UTF-8.
  • Timestamps are numbers: milliseconds since 1970-01-01T00:00:00Z (Unix epoch). The only exception is exportedAt in the header, which is an ISO 8601 string in UTC.
  • Identifiers are the identifiers Jira uses in its public REST API (issue keys, comment, attachment and link IDs, transition and status IDs, Atlassian account IDs). They can be resolved with the Jira Cloud REST API v3.

3. Document structure

{
  "app": "Stitchback – Merge & Undo for Jira",
  "format": "stitchback-export/1",
  "exportedAt": "2026-10-04T12:00:00.000Z",
  "retentionDays": 90,
  "items": [
    { "key": "merge:<merge ID>", "value": { } },
    { "key": "running:<issue key>", "value": { } },
    { "key": "runlock:<merge ID>", "value": { } },
    { "key": "retention:cursor", "value": { } }
  ],
  "lookup": [
    { "key": "last:<issue key>", "value": "<merge ID>" }
  ]
}
FieldMeaning
app, formatProduct name and format version. A change that is not backwards compatible gets a new format version
exportedAtTime of the export
retentionDaysRetention period applied by the installation
itemsAll stored entries except the last: entries, as key–value pairs, in storage order
lookupThe last: entries (Section 4), as key–value pairs. items and lookup together hold every stored key

4. Keys

KeyValue
merge:<merge ID>The merge record (Section 5)
running:<issue key>Lock while a merge of this source issue is running: { "id": <merge ID>, "at": <timestamp> }
last:<issue key>ID of the most recent merge in which this issue was source or target
runlock:<merge ID>, undolock:<merge ID>Lock for one stage of a merge or of an undo: { "token": <random string>, "until": <timestamp> }. No personal data. Expired locks are removed by the daily clean-up
retention:cursorWhere the daily clean-up stopped: { "phase", "after", "at" }. Internal position marker, no personal data

FieldContent
vVersion of the record structure (currently 3)

sourcekey, isServiceRequest, statusBefore (status of the source before the merge), hadResolution (whether the source had a resolution before the merge)

The warnings of the preview, which name people and files, are shown on screen and not stored

6. Step

Each step has state (pending, done, failed or skipped) and the fields below that apply to its operation op:

FieldContent
op, phaseOperation (copyComment, copyAttachment, mentionAttachment, addLink, addParticipant, addWatcher, linkDuplicate, auditComment, closeSource) and its phase
issueIssue key the step acts on
fromID of the original item in the source issue
internal, visibilityWhether the copied comment is internal; its role or group restriction
attachmentId, sizeID and size in bytes of the original attachment
type, direction, otherKey, existingLinkIdsLink type, direction, linked issue key, IDs of links that already existed
accountIdAccount ID of the requester added as participant or watcher
duplicateOfTarget issue key for the duplicate link
transitionId, toStatusIdJira transition and status used to close the source

When a step has created something, created records the IDs of the created items (for example the new comment, attachment or link), so that undo can remove exactly those.

7. What is not in the export

The Product does not store display names, issue summaries, file names, comment or attachment content, or email addresses (Privacy Policy, Section A3). This content stays in the Customer's Jira site and can be exported there with Jira's own tools.
